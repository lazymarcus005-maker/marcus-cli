A

Core Concept

หลักการที่ไม่ต่อรอง · spec §3, §5.1–5.6

หลักการด้านล่างนี้เป็น "ข้อสัญญา" ที่บังคับใช้กับทุกโมดูล ไม่ใช่แนวทางที่เลือกทำได้

spec §3.1 · §3.4

Lightweight first, minimal Pi fork

หลีกเลี่ยง infrastructure ที่ไม่จำเป็น — ไม่มี vector DB, Neo4j, embedding server, background indexer, docker, cloud และ "หลีกเลี่ยงการแก้ Pi internals โดยไม่จำเป็น" ลำดับที่ยอมรับ: supported SDK composition → wrapper → documented core patch (เมื่อมี API gap ที่พิสูจน์แล้วเท่านั้น)

เบาที่สุด และไม่ fork Pi ถ้าไม่จำเป็นจริง ๆ

spec §3.2 · §6.3 · §13

Deterministic retrieval before AI retrieval

ไล่จาก Working Set → ripgrep → Symbol Index → References → Code Graph → Git History → (optional) semantic search และ "ไม่ใช้ LLM เพื่อ search/rank ถ้า deterministic method สามารถทำได้" — ไม่มีการเรียก LLM เพิ่มเพื่อจัดอันดับงานประจำ

ค้นหาแบบ deterministic ก่อนเสมอ, LLM เป็นทางเลือกสุดท้าย

spec §3.3 · §6.5 · §46

Context is a budget

Context window ไม่ใช่พื้นที่ที่ต้องใช้ให้เต็ม จัดเรียงตาม relevance, token cost, task ปัจจุบัน, workflow stage, การเปลี่ยนแปลงปัจจุบัน และข้อจำกัดของโมเดล เป้าหมายหลักคือ "minimum sufficient context for correct action" และคุณภาพต้องไม่ถูกแลกกับ token อย่างเงียบ ๆ

งบ context ต้องถูกคำนวณ ไม่ใช่เดา และห้ามตัดทิ้งแบบเงียบ

handoff §5.4 · spec §33–34 · §30

Approval-gated execution

ทุก executable path — Pi built-in tools, custom tools, extensions — ผ่าน Policy Executor ทางเดียว command ที่ไม่รู้จักหรือ effect นอกขอบเขตต้องได้รับอนุญาตชัดเจน และ noninteractive ต้อง "fail closed" ไม่มี hard reset, force push หรือ destructive rollback อัตโนมัติ

ทุกอย่างที่รันได้ต้องขออนุญาตก่อน และปิดประตูเมื่อไม่มีการยืนยัน

spec §5.5–5.6 · §20 · §38

Durable state & honest uncertainty

state.db เป็น transactional authority ที่ journal intent ก่อน launch และผลที่สังเกตได้หลังจบ สถานะที่พิสูจน์ไม่ได้ต้องเป็น unknown ไม่ใช่ success: output ที่ไม่ครบ, timeout, cancellation, ไม่มี test, parser ไม่รองรับ ล้วน "ไม่ใช่ pass" — และ checkpoint กู้คืนแค่ agent state ไม่กู้ source bytes

ความไม่รู้ต้องรายงานว่า unknown เสมอ ห้ามเดาว่าสำเร็จ

โมดูลเดียว (single package) · ขอบเขตเป็น logical module · spec §4, §41

C

Three Flows That Define The System

ทุก request · ทุกคำสั่งที่รัน · ทุก run

สามเส้นทางนี้คือที่มาของ gate ส่วนใหญ่ในสเปก — ถ้าเส้นใดเส้นหนึ่งผิด คุณภาพหรือความปลอดภัยจะพังทันที

C1 · Per-request context pipeline

spec §6 — รันก่อน ทุก provider request

รวมถึง request ซอยย่อยภายใน Pi run เดียว — ไม่ใช่แค่ตอนขึ้น turn ใหม่

1

Load

โหลด intent, instructions ที่ใช้ได้ และ tool-protocol obligation ที่ค้างอยู่

2

Validate

ตรวจ hash ของ candidate source และความสดของ cached evidence

3

Merge

รวม context ใหม่กับ retained history, dedupe, ระบุเวอร์ชันที่ถูกแทนที่แล้ว

4

Rank & budget

จัดอันดับ deterministic แล้วใช้งบ — ถ้าไม่พอจริงให้ pause ไม่ใช่ตัดเงียบ

5

Validate shape

ตรวจลำดับเวลา, การจับคู่ tool-call/result และข้อจำกัดของ provider

6

Manifest & dispatch

บันทึก request manifest แล้วส่ง view ที่ผ่านการตรวจผ่าน kernel

C2 · Tool execution lifecycle

spec §17, §33–34, §38

journal intent ก่อน launch เสมอ — crash ระหว่างทางจึงกลายเป็น unknown ไม่ใช่การเดาว่าสำเร็จ

1

Authorize

ขออนุมัติ command · นอกขอบเขตหรือ noninteractive → fail closed

2

Journal

commit prepared ก่อน launch: execution id, Pi tool-call id, input ที่ redact แล้ว, precondition

3

Capture

spawn ด้วย environment allowlist แล้ว stream output แบบ bounded ลง disk

4

Settle

completed / failed / cancelled / unknown — cancellation ยิงถึง process group พร้อม grace 2 วินาที

5

Evidence → invalidate

บันทึก evidence พร้อม snapshot digest · การแก้ไฟล์ที่เกี่ยวข้องภายหลังทำให้ evidence เก่าใช้ไม่ได้

C3 · Run lifecycle, compaction & recovery

spec §5.2, §20–21, §35, §38

Harness เป็นเจ้าของ "จะไปต่อหรือหยุด" ส่วน Pi เป็นเจ้าของ inner model/tool loop

Workflow

understand → discover → plan → implement → test → inspect/fix → review → finish · re-plan เฉพาะเมื่อ task เปลี่ยน, เจอ blocker ใหญ่ หรือสมมติฐานแรกผิด

Stop / pause conditions

งานเสร็จ · blocker · policy denial · user cancellation · failure ซ้ำโดยไม่มีความคืบหน้า · ถึงเพดานที่ตั้งไว้ · "ห้ามไปต่อ run ที่ถูกยกเลิกอัตโนมัติ"

Compaction (Macus คุมเอง)

ถึง safe tool boundary → commit task/ledger state → checkpoint → สั่ง Pi compact → validate + rebuild effective view → ไปต่อเฉพาะเมื่อ invariant ยังจริง · serialize กับการ dispatch

Recovery order

ยึด mutation lock → ตรวจ identity ของ repo/worktree/session → โหลด transcript + state revision → reconcile journal กับหลักฐานจริง → แก้ incomplete tool exchange ผ่าน adapter ที่รองรับ (ถ้าไม่ได้ → pause ไม่แก้ไฟล์ Pi) → revalidate hash/evidence → resume เฉพาะงานที่ได้รับอนุญาต

กติกาที่ทำให้ recovery ซื่อสัตย์

"ห้ามสมมติว่าคำตอบที่หายไปแปลว่าคำสั่งไม่ได้รัน" · ผลลัพธ์ที่สำเร็จแล้ว restore ได้ครั้งเดียว · ผลที่ไม่ชัดเจนยังเป็น unknown

Checkpoint ที่ไม่หลอกตัวเอง

atomic write + rename + register ใน state.db · "ห้ามถือว่า checkpoint ที่ไม่สมบูรณ์คือ committed" · restore ทำให้ evidence เก่า invalid แต่ไม่ revert โค้ด

D

Harness Engineering

spec §39, §45 · handoff §14

คำว่า “harness” ในโปรเจกต์นี้มี สองความหมาย และทั้งคู่คือหัวใจของงานวิศวกรรม: (1) Agent Harness = ชั้นควบคุม run/workflow แบบ durable ใน panel B–C และ (2) Benchmark Harness = เครื่องมือวัดผลแบบ paired ที่ต้องพิสูจน์ว่าการลด context ไม่ทำลายคุณภาพ

D1 · Paired measurement harness

workflow/benchmark.ts · runPairedBenchmark()

Macus กับ Pi เวอร์ชันดิบถูกวัดบนเงื่อนไขเดียวกัน แล้วสลับลำดับเพื่อตัดอคติของ cache/เวลา

1

Same inputs

revision เริ่มต้น, prompt, endpoint/version ของโมเดล, generation settings, context/output limits และ test oracle เดียวกัน

2

Reset workspace

reset ระหว่าง run ทุกครั้งผ่าน prepareWorkspace ที่เป็น dependency ชัดเจน

3

≥3 repetitions

อย่างน้อย 3 คู่ต่อ task/condition · safety bound 2,000 runs ต่อแผน

4

Alternate order

repetition คู่ → unmodified_pi ก่อน; คี่ → macus ก่อน (สลับจริงในโค้ด)

5

Label cache

แยก repository cache และ provider cache เป็น cold / warm / unknown — ที่ควบคุมไม่ได้ต้องเป็น unknown

6

Correctness first

วัด task success ก่อน แล้วจึง tokens ทั้งหมด (รวม summary/retry/compaction), wall time, first useful edit, peak context, CLI memory

Quality gate

ต้อง "ไม่มี test case ของ correctness/recovery ที่พังเพิ่มขึ้น" เทียบ baseline — เป็น regression gate ไม่ใช่หลักฐานทางสถิติว่าเทียบเท่า

ห้ามอ้าง token/latency ดีขึ้นนอกเงื่อนไขที่วัด

Reference fixture

ชุดทดสอบผสม TS/JS/C# ขนาด 10,000 ไฟล์ ~100 MiB พร้อม SHA-256 manifest และรายการ exclusion ที่ deterministic

workflow/benchmark-fixture.ts

Metric distributions

เก็บ raw run data และกระจายค่าต่อ task × condition × system ไม่ใช่ค่าเฉลี่ยค่าเดียวที่ซ่อนความแปรปรวน

โดยเก็บ cost เฉพาะเมื่อมีแหล่งราคาชัดเจน

D2 · Evidence & phase gates

spec §45 — ตาราง phase คือสัญญา

เจ็ด phase แต่ละอันมี gate ของตัวเอง และทุก phase ปิดได้เฉพาะเมื่อมีหลักฐานที่ทำซ้ำได้

1 · Agent foundation & safety

ทุก adapter hook ถูกพิสูจน์ · ทุก request อยู่ใน budget · cancel ถึงจริง · crash หลังเขียนไม่ replay

2 · Retrieval & freshness

symbol กำกวมต้อง explicit · ไฟล์ถูกแก้/ลบ/เปลี่ยนชื่อต้อง refresh · hash เก่าห้าม drive edit

3 · Context runtime

request ที่ส่งจริงตรงกับ manifest · อ่านซ้ำไม่ทำ source ซ้ำ · สลับไปโมเดลเล็กยังอยู่ใน budget

4 · Workflow & evidence

task รอดจาก resume · ผล partial/unknown/timeout/ไม่มี test ห้ามผ่าน · loop caps ทำงาน

5 · Durable context

goal/constraint/tool obligation รอดจาก compaction · failure ยังกู้คืนได้ · restore ทำให้ evidence เก่า invalid โดยไม่ revert โค้ด

6 · Relationships

ชื่อซ้ำ/alias/overload/dynamic call ห้ามให้ความมั่นใจเท็จ · graph ปิดแล้ว search/workflow ยังทำงาน

7 · Release hardening

gate ก่อนหน้าทั้งหมดยังเขียว · ติดตั้งสะอาด · recovery interruption matrix ผ่านหรือ pause อย่างชัดเจน · เผยแพร่ metrics/ข้อจำกัด

Common gate ทุก phase

CLI ทำงาน · test/typecheck/build ผ่าน · lint ถ้ามี config · docs อัปเดต · diff ถูก review · ไม่มี unrelated change · เขียน docs/phase-N-evidence.md

กฎของการรายงานผล (ห้ามละเมิด)

  • คำสั่งที่ fail หรือ required test ที่ไม่ได้รัน ปิด phase ไม่ได้ — "no placeholder success statements"
  • ผลรวมของ search ที่ไม่รู้จำนวนต้องเป็น nullable — "ห้ามอ้าง total ที่แน่นอนถ้าไม่ได้นับจริง"
  • ความเชื่อมั่นเป็นเพียง evidence/ranking hint ไม่ใช่ probability ที่ calibrate แล้ว
  • ตัวเลข performance ทั้งหมดเป็น target ที่ต้องวัด ไม่ใช่ผลที่ได้แล้ว (startup p95 < 2 s, search p95 ≤ 500 ms, symbol read p95 ≤ 200 ms, index refresh ไฟล์ ≤ 100 KiB p95 ≤ 1 s, idle CPU < 1%, peak RSS ≤ 512 MiB)
  • ถ้าวัดบนเครื่องอื่น ต้องรายงานแยกหรือ rebaseline ด้วยหลักฐาน — "ห้ามผ่อนเป้าหมายเงียบ ๆ"
  • mock provider พิสูจน์ได้แค่พฤติกรรมในเครื่อง ไม่ใช่ compatibility กับ provider จริง
